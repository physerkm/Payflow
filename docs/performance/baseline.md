# Performance baseline

A measured starting point (spec §16, PF-050, week 7 "k6 load test and SQL tuning"). These are numbers from one
developer machine, not an SLA. Re-run the same steps on staging before drawing capacity conclusions.

**Measured on 2026-11-09** with the commit that added this file.

## Environment

| | |
|---|---|
| Host | Windows 11, Docker Desktop 4.98 (WSL 2), 16 vCPU, 8 GB for the Docker VM |
| Stack | `docker compose --profile observability up` - API and Worker in Release containers, PostgreSQL 17, RabbitMQ 4, OpenTelemetry export on |
| Load generator | k6 1.0.0 in a container on the compose network (`http://api:8080`), so Windows port forwarding is not measured |
| Rate limiting | Off for the run (`RATE_LIMITING_ENABLED=false`): the test uses one user, which exceeds the 600 req/min per-user limit by design |

## 1. k6 load test

Script: [`tests/load/k6/baseline.js`](../../tests/load/k6/baseline.js), 1 minute:

- **readers**: 20 virtual users, each loading the first page of orders, payments and customers, then pausing 0.5 s.
- **payers**: 5 orders per second, each followed by a payment (`pm_test_success`, with an `Idempotency-Key`).

| Metric | Result | Target (spec §16) |
|---|---|---|
| Read requests (6 777) - p50 / p95 / p99 | 8.2 ms / **23.0 ms** / **47.1 ms** | p95 < 500 ms ✓ |
| Read requests - error rate | **0 %** | < 1 % ✓ |
| Payment initiation (301) - p50 / p95 / p99 | 10.2 ms / 26.3 ms / 57.8 ms | - |
| Payments accepted (202) | **301 / 301** | > 99 % ✓ |
| Throughput | 119 requests/s | - |

What happened behind the API during the run (Prometheus, same time window):

| Signal | Peak during the run |
|---|---|
| Outbox pending messages / oldest pending age | 1 / 16 ms |
| RabbitMQ ready messages (all queues) | 0 |
| Worker processing p95 for `PaymentRequested.v1` (includes the simulated provider latency) | 236 ms |
| PostgreSQL sessions waiting for a lock | 0 |
| API connections in use (pool max 100) | 7 |
| Payments of the run that ended `Succeeded` | 301 / 301 |

The asynchronous side kept up with the write rate: messages were published and consumed as fast as they were
produced, and no payment was left in an open state.

## 2. Query plans at volume

Script: [`tests/load/sql/explain-baseline.sql`](../../tests/load/sql/explain-baseline.sql). It adds 100 000 orders,
order items, payments and attempts to one tenant, plus 150 000 outbox rows (50 000 pending, as after a broker
outage), runs `EXPLAIN (ANALYZE, BUFFERS)` and **rolls everything back**. Tenant queries run as `payflow_app` with
Row-Level Security and the tenant context set, exactly like the API.

| # | Query (as generated by EF Core) | Plan | Execution time |
|---|---|---|---|
| Q1 | Orders list, first page, with item count | Index Scan `ix_orders_tenant_created` + Index Only Scan `ix_order_items_tenant_id_order_id` per row | **0.55 ms** |
| Q2 | Orders total count for pagination | Seq Scan (the tenant is the whole table) | **15.4 ms** |
| Q3 | Payments list, first page, with attempts | Index Scan `ix_payments_tenant_created` → Nested Loop on `ux_payment_attempts_payment_number` | **0.30 ms** |
| Q4 | Payments filtered by status, page 50 | Index Scan `ix_payments_tenant_created` + status filter (9 301 rows skipped) | **1.4 ms** |
| Q5 | Outbox poll, `FOR UPDATE SKIP LOCKED`, 50 000 pending | Index Scan on the partial index `ix_outbox_pending` (`available_at, created_at WHERE status = 'Pending'`) | **0.09 ms** |

In every plan the RLS predicate is a one-time filter
(`NULLIF(current_setting('app.tenant_id', true), '')::uuid = …`), evaluated once per query and not per row.

### Findings

- **No index changes needed.** Every list query reads only the rows of the requested page through a
  tenant-prefixed index; the outbox poll stays constant-time with a large backlog thanks to the partial index.
- **The pagination count grows with tenant size** (Q2: 15 ms at 100 000 orders, linear). Acceptable for the MVP.
  For tenants with millions of orders, switch the lists to keyset pagination ("load more") or show an estimated
  total. Tracked as a known limitation in the README.
- **Rare statuses on deep pages** (Q4) scan the created-at index and filter. With the 10 % failure rate used here
  this costs 1.4 ms; `ix_payments_tenant_status` covers the rare-status case.

## Reproduce

```bash
# 1. Stack with rate limits off for the load test
RATE_LIMITING_ENABLED=false docker compose --profile observability up -d --build

# 2. Load test (k6 in a container; results in tests/load/results/, git-ignored)
docker run --rm --network payflow_default -v "$PWD/tests/load:/load" grafana/k6:1.0.0 \
  run -e BASE_URL=http://api:8080 --summary-export /load/results/summary.json /load/k6/baseline.js

# 3. Query plans at volume (needs the tenant created by step 2; leaves no data behind)
docker compose exec -T postgres psql -U payflow -d payflow -f - < tests/load/sql/explain-baseline.sql

# 4. Back to normal rate limits
docker compose --profile observability up -d api
```

While the test runs, watch Grafana → *PayFlow - Operations* (http://localhost:3000): request rate and latency,
outbox backlog, queue depth, worker processing time, DB connection pool and lock waits.
